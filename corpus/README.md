# GIF decoder corpus

Eight small GIFs, each built to break a decoder in a specific way. They exist because
`index.html` carries its own GIF decoder rather than routing GIF through `ImageDecoder`, and
that decision only pays off if the decoder is actually right. Section 6 of [`PLAN.md`](../PLAN.md)
names these cases; this directory is them.

Nothing here is a fixture captured from the wild. Every file is generated by
[`make_corpus.py`](make_corpus.py), byte by byte, with no imaging library — the fields that
matter (the interlace flag, disposal method 3, per-frame local colour tables, sub-rectangle
placement) are exactly the ones a library chooses for you.

```
python3 corpus/make_corpus.py
```

Regenerating is deterministic: the same bytes come out every time, so a diff in these files
means the generator changed.

## The files

| File | Bytes | Frames | What it breaks |
|---|---|---|---|
| `01-interlaced.gif` | 279 | 2 | Four-pass interlace row ordering |
| `02-disposal-2.gif` | 144 | 3 | Disposal 2, restore to background |
| `03-disposal-3.gif` | 166 | 3 | Disposal 3, restore to previous |
| `04-local-palettes.gif` | 213 | 3 | Local colour tables overriding the global one |
| `05-subrect.gif` | 197 | 4 | Sub-rectangle frames at non-zero x/y |
| `06-delay-zero.gif` | 201 | 4 | The sub-20ms delay clamp, and its exact boundary |
| `07-single-frame.gif` | 66 | 1 | A still: no GCE, and no timeline boundaries |
| `08-first-frame-partial.gif` | 144 | 3 | A first frame smaller than the canvas |

1410 bytes for the set. Each is designed so that a failure is *obvious* rather than subtle:

**`01`** fills row *y* with palette index *y*, a monotonic grey ramp. Any pass mis-ordered
produces a non-monotonic column rather than something that merely looks a bit wrong.

**`02`** places three squares that never overlap. Each output frame must show exactly one; a
decoder that ignores disposal 2 accumulates all three into a staircase.

**`03`** draws a background, overlays a green square asking for disposal 3, then draws a third
frame. Frame 3 must show the background plus its own square and *no trace of the green*.
Disposal 3 is rare in the wild and correspondingly often wrong.

**`04`** fills every frame with index 1. The global table calls index 1 red; the two local
tables call it green and blue. A decoder that ignores local tables renders three red frames —
a failure that looks like a boring animation rather than an error.

**`05`** uses offsets and sizes that are deliberately not multiples of 8 and not aligned to each
other (`5,7,6×9`, `17,3,11×4`, `20,20,12×12`), so a row-stride off-by-one lands somewhere
visible instead of cancelling out.

**`06`** carries delays of 0, 1, 2 and 5 centiseconds. The first two are below the 20 ms
threshold and must both come back as 100 ms; 2 cs sits *exactly* on the boundary and must stay
20 ms. See the note on the clamp below — it is the one place the two decoders disagree, by
design.

**`07`** has no graphic control extension at all, exercising the decoder's fallback, and must be
treated as static so that it contributes no boundaries to the merged timeline.

**`08`** has a first frame of 8×8 at (8,8) on a 24×24 canvas. A decoder that assumes frame zero
covers the canvas leaves the margin opaque or uninitialised; it must be fully transparent.

## Expected results

[`expected.json`](expected.json) records, per file, the frame count, the per-frame delay in
milliseconds *after* the decoder's clamp, and a set of pixel probes. The probes come from the
drawing plan in the generator — what each frame is *meant* to contain — not from decoding the
output, so they state intent rather than restating whatever the encoder happened to emit.

## Verification

Each file was run through three independent things, which must agree:

1. **Intent** — `expected.json`, derived from the drawing plan.
2. **The repository's decoder** — `parseGIF` + `flattenGIF` from `index.html`.
3. **The browser's own GIF decoder** — `ImageDecoder` with `image/gif`, frames composited to a
   canvas. This is the useful oracle precisely *because* the tool deliberately does not use it:
   it shares no code with the decoder under test.

Run against `https://overlay.immanuelqrw.dev` on 2026-09-02 (`ImageDecoder` needs a secure
context, so `file://` will not do for step 3):

contributes no boundaries to the merge.

### The one intentional disagreement

On `06`, the two decoders report different timings, and that is correct:

| Frame | In the file | `ImageDecoder` | This decoder |
|---|---|---|---|
| 0 | 0 cs | 0 ms | **100 ms** |
| 1 | 1 cs | 10 ms | **100 ms** |
| 2 | 2 cs | 20 ms | 20 ms |
| 3 | 5 cs | 50 ms | 50 ms |

`ImageDecoder` reports what the file literally says. `realDelay()` reports what the animation
actually *looks like*, because browsers clamp GIF delays of 0 or 1 centisecond to roughly
100 ms when rendering. The preview has to match the source as played, not as written — see
section 3 of [`PLAN.md`](../PLAN.md). A future change that makes these two columns agree has
broken the preview, not fixed the decoder.

## Not covered here

Worth knowing before this is treated as complete coverage:

- **Transparent index within a frame.** Every frame here is opaque; `02` and `08` rely on
  never-written pixels for their transparency, not on a transparent palette entry. See #60.
- **LZW dictionary reset.** The files are small enough that the code size never widens past the
  first bump, so the 4096-entry clear path is untested. The generator implements it. See #60.

Malformed input — truncated streams, corrupt LZW, absurd dimensions — is covered by
`test/malformed.spec.js` (#55) rather than by files here. Those inputs are derived from
`05-subrect.gif` at test time: "truncated to half of 05-subrect.gif" says what it is, where a
committed blob with the same bytes would not, and it keeps this directory meaning *valid* GIFs
that exercise a decode path.
